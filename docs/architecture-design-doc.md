# Real-Time Event Processing & Analytics Platform — Architecture & Design Document

Status: pre-implementation design. Nothing in this document has been built or verified yet.
Each decision below is tagged with the build step (see build plan) where it gets tested against
real terminal output. Claims here are hypotheses until then, not facts.

Scope for the initial build: Kafka, Flink, Postgres, Prometheus, Grafana, and a Python producer/API.
ClickHouse and ML-based anomaly detection are explicitly deferred (see "Deferred Decisions").

---

## 1. Event Schema

```json
{
  "event_id": "evt_8f31a91c",
  "user_id": "usr_10291",
  "merchant_id": "merchant_482",
  "amount": 125000,
  "currency": "NGN",
  "transaction_type": "purchase",
  "event_time": "2026-08-17T10:30:22.481Z",
  "ingest_time": "2026-08-17T10:30:22.900Z",
  "schema_version": 1
}
```

Design decisions:

- **`event_id` is the deduplication key.** Generated by the producer (UUID-based), not by Kafka
  or Flink, so retries at any layer are safely identifiable as duplicates.
- **`event_time` vs `ingest_time` are separate fields.** `event_time` is what Flink's watermark
  strategy operates on — it represents when the transaction actually happened, and may arrive
  late or out of order. `ingest_time` is only for debugging pipeline latency, never used for
  windowing logic.
- **`schema_version` from day one.** Even a single-producer toy system benefits from this,
  because it forces validation logic in Flink to reject or route unknown versions explicitly
  instead of silently misparsing them later.
- **Amounts are integers (minor units), not floats.** Avoids floating-point drift in aggregates —
  same reasoning as any financial system.

Open question to settle before Step 2: whether malformed-event injection in the producer
corrupts the schema at the JSON level (missing fields, wrong types) or at the semantic level
(negative amounts, invalid currency codes) — both are needed, but Flink's validation operator
needs to know which failure mode it's built to catch.

## 2. Kafka Topology

### Topics

| Topic | Purpose |
|---|---|
| `transactions.raw` | Producer writes here. Source of truth, untouched. |
| `transactions.deadletter` | Validation failures land here with a reason code, not dropped silently. |
| `transactions.late` | Events that arrive past allowed lateness — side output, not discarded. |
| `analytics.aggregates` | Flink's windowed aggregate output, for downstream consumers beyond Postgres. |

Keeping a dead-letter and a late-events topic instead of dropping either matters for the
failure-injection work in Step 9 — you can't measure "events lost" honestly if the pipeline
throws them away before you can count them.

### Partition key: `user_id`

Chosen because:

- Per-user velocity detection and per-user rolling aggregates are the core stateful operators.
  Keying by `user_id` guarantees all of one user's events land on the same partition, which
  guarantees Flink sees them in Kafka-partition order and can keep per-user state local
  (no cross-partition state lookups).
- The alternative, keying by `event_id` (or round-robin), would maximize partition-level
  throughput evenly but destroys per-user ordering — velocity detection would then require
  a shuffle/keyBy inside Flink anyway, just moving the cost rather than removing it.

Known risk, to be measured not assumed: if the load generator's user distribution is skewed
(a small number of high-frequency users), those partitions become hot and bound the consumer's
effective throughput regardless of total partition count. The load generator's "event
distribution" config (Step 2) should include a skewed-distribution mode specifically so this
can be provoked and measured, not just theorized about.

### Other settings (initial values, to be tuned against Step 12 benchmarks)

- **Partition count:** start at 6 for `transactions.raw` — enough to parallelize across a
  small Flink cluster without over-partitioning a single-broker dev setup.
- **Replication factor:** 1 for the scaled-down dev environment (single broker), explicitly
  documented as a gap — production would need ≥3. This mirrors how the API project documented
  the 30-connection Postgres pool ceiling honestly rather than pretending it wasn't there.
- **Producer acks:** `all`, with `enable.idempotence=true`. This is the Kafka-side half of the
  exactly-once story — the Flink-side half (checkpointing, transactional sinks) is in Section 5.
- **Consumer groups:** one group per logical Flink job, so re-running a job for testing doesn't
  fight over offsets with a "live" instance.
- **Retention:** short (24–48h) for dev — this is a demo pipeline, not a durable log store.
- **Compression:** `snappy` on the producer, cheap CPU cost for meaningfully smaller batches.

## 3. Flink Pipeline

```text
Kafka source (transactions.raw)
        │
        ▼
Validation  ──(invalid)──► transactions.deadletter
        │
        ▼
Deduplication (keyed by event_id, TTL'd state)
        │
        ▼
Watermark assignment (bounded out-of-orderness on event_time)
        │
        ▼
keyBy(user_id)
        │
   ┌────┴────┐
   ▼         ▼
Windowed    Per-user velocity /
aggregates  anomaly detection
   │         │
   ▼         ▼
Postgres    Postgres (anomalies table) + Kafka (analytics.aggregates)
```

### Deduplication

Keyed state on `event_id`, with a TTL slightly longer than the maximum allowed lateness — an
event_id doesn't need to be remembered forever, only long enough to catch realistic duplicate
windows. This is a deliberate tradeoff: unbounded dedup state would be "more correct" in theory
but unbounded state growth is itself a failure mode worth avoiding, and the spec doesn't call
for infinite-horizon exactly-once, just correctness within the pipeline's operating window.

### Watermark strategy

Bounded out-of-orderness watermarks on `event_time`, with allowed lateness on the windows
downstream. Two numbers need to be picked and then justified against real producer behavior
in Step 5, not guessed in the abstract:

- **Out-of-orderness bound:** how far behind the max-seen event_time a watermark trails.
- **Allowed lateness:** how long after a window closes a late event can still update it before
  being routed to `transactions.late` instead.

These two numbers directly trade off latency (how soon can we emit a "final" aggregate) against
completeness (how many legitimately late events get included). The producer's own configurable
delay/out-of-order settings (Step 2) exist specifically so this tradeoff can be tuned against
observed data rather than picked arbitrarily.

### Windowing

Tumbling windows at 10s / 1m / 5m / 1h, keyed by `user_id` for per-user aggregates and
by `merchant_id` for merchant-volume aggregates — these are two separate keyed streams off
the same deduplicated source, not one window doing both jobs.

### Anomaly detection (deterministic, not ML)

Two rules, both stated in the original spec:

1. Per-user transaction count in a rolling window exceeds a threshold (velocity).
2. Transaction amount exceeds the user's rolling 99th-percentile amount.

Rule 2 requires maintaining a rolling percentile estimate in keyed state — worth flagging now
because it's meaningfully more state-heavy than rule 1, and if state size becomes a checkpoint-
duration problem in Step 12, this is the first place to look.

## 4. State Management

- **State backend:** RocksDB, not the heap-based backend — even at dev scale, this is the
  backend that actually exercises incremental checkpointing, which is part of what's being
  demonstrated here (the point isn't just "it works," it's "it works the way production would").
- **State touchpoints:** dedup state (event_id → seen), windowed aggregate state, per-user
  velocity counters, per-user rolling percentile estimate.
- **State size is a benchmark variable, not an afterthought** — Step 12 should report state
  size alongside throughput/latency, since it directly explains checkpoint duration.

---

## 5. Checkpointing & Exactly-Once

- **Checkpoint interval:** start at 10s. Short enough to bound recovery-time-on-failure,
  long enough not to dominate the pipeline with checkpoint overhead — this exact number gets
  revisited once Step 8's kill-test produces a real recovery-time number.
- **Checkpointing mode:** exactly-once (aligned checkpoints to start; unaligned is a documented
  follow-up if backpressure during checkpointing becomes a measured problem, not a default).
- **Checkpoint storage:** durable volume, not in-memory — a checkpoint that can't survive the
  TaskManager it was protecting against dying is not doing its job.

### What "exactly-once" actually covers here — stated explicitly, not implied

Flink's exactly-once checkpointing guarantees **internal state consistency**: if a TaskManager
dies and recovers from checkpoint, Flink's own counters/windows/dedup-state are exactly as if
the failure hadn't happened. That is not the same claim as **end-to-end exactly-once**, which
depends entirely on the sink:

- **Postgres sink:** exactly-once only if the sink is idempotent (upsert keyed by `event_id`)
  or transactional (two-phase commit tied to Flink's checkpoint barrier). Plain inserts under
  at-least-once restart semantics will duplicate rows even with Flink's internal state correct —
  this is the exact failure mode the design doc's own spec warns about, and it's worth stating
  in writing now so Step 7/8 gets built with an idempotent upsert from the start, not retrofitted.
- **Kafka sink (`analytics.aggregates`):** transactional producer, `read_committed` isolation
  on any downstream consumer of that topic.
- **Dead-letter/late topics:** these are diagnostic outputs, not part of the exactly-once
  contract — duplicates there are acceptable and not counted against the guarantee.

## 7. Failure Scenarios (to be executed in Step 9, listed here for design completeness)

For each: failure → detection mechanism → recovery mechanism → events replayed →
events lost → duplicates produced → recovery time.

- Flink TaskManager crash mid-processing
- Kafka broker failure (single-broker dev setup: this one will be destructive by
  construction — worth stating now that a real test needs ≥3 brokers, another documented gap)
- Producer failure / restart
- Network interruption between Flink and Kafka
- Postgres unavailability during sink write
- Consumer group restart with offset reset variations

## 8. Benchmark Methodology (executed in Step 12)

Load levels: 1k / 5k / 10k / 50k / 100k events/sec, bounded by whatever the Codespace machine
type actually allows — reported honestly rather than extrapolated.

Metrics per load level: throughput, P50/P95/P99 latency, Kafka consumer lag, checkpoint
duration, recovery time after induced failure, duplicate count, lost-event count.

Hardware and Codespace machine type documented alongside every result table — a number without
its hardware context is not a benchmark.

## 9. Deferred Decisions

- **ClickHouse:** only added if Step 12 benchmarks show a concrete Postgres analytical-query
  limitation (e.g., aggregate query latency degrading past a stated threshold under load).
  If Postgres holds up, that's the documented finding — not a reason to add ClickHouse anyway.
- **ML-based anomaly detection:** only considered after the deterministic rules (Section 3) are
  measured against realistic false-positive/false-negative rates. No ML until the simple
  version's limitations are demonstrated, not assumed.
